The big picture

A global planner is the robot's navigation app. You give it a map, where the robot is and where it must go; it returns the cheapest route. "Cheapest" can mean shortest, fastest, safest or least energy — whatever cost you attach to each move. The rest of the lecture answers the practical follow-up questions: how to search faster, what to do when there isn't time to find the very best route, what to do when the map changes or the robot has already moved, how to cope with enormous maps, and who decides when to drive on, wait or replan.

In the course stack of Lecture 1, global planning sits between state estimation and control. It takes the estimated position and the map and hands a route to the local planner (next week), which turns it into a smooth, drivable trajectory for the controller.

Graphs and the shortest-path problem

Turn the map into dots and arrows. A dot (node) is a place or state the robot can be in — a grid cell, a road intersection, a parking spot. An arrow (edge) is a move that is allowed from one node to another, and its number (cost) is what that move costs. A route is a chain of arrows from start to goal; its cost is the sum of the arrow costs. The planner looks for the chain with the smallest sum.

$$\mathcal{G} = (V, E), \qquad c(u,v) \ge 0, \qquad P = (v_0 = S, \dots, v_k = G), \qquad J(P) = \sum_{i=0}^{k-1} c(v_i, v_{i+1})$$

$V$ is the set of states (nodes), $E$ the set of allowed moves (edges), $S$ the start, $G$ the goal and $k$ the number of edges in the path. Goal: find the path $P$ that minimizes $J(P)$. Edges have a direction (a one-way street is an edge in one direction only), and every cost in this lecture is non-negative.

Listing routes works here, but the number of routes explodes with map size: a 20 × 20 grid already has about 1.4 × 1011 shortest-length corner-to-corner routes. The algorithms below never list routes — they build the cheapest cost to each node one step at a time.

Every part of a shortest path is itself a shortest path. If S→A→B→C→G is cheapest to G, then S→A→B must be the cheapest way to B — otherwise you could swap in the cheaper piece and beat the "cheapest" route. That is why shortest costs can be built node by node and reused.

Relaxation: the one update everything uses

For every node, keep a running record: "the cheapest way I have found to get here so far" ($g$) and "which node I came from" (parent). Relaxing an edge u→v asks one question: would arriving at v through u beat the record? If yes, overwrite the record. Dijkstra, A*, ARA*, LPA* and D* Lite are all just different orders in which to ask this question.

$$g(u) + c(u,v) < g(v) \;\Rightarrow\; g(v) \leftarrow g(u) + c(u,v), \qquad \mathrm{parent}(v) \leftarrow u$$
  • $g(v)$: lowest cost of an S→v path found so far — the value being updated. It starts at ∞ for every node except $g(S) = 0$.
  • $c(u,v)$: the given edge cost.
  • parent records the path; it never deletes an edge from the graph. Following parents back from G and reversing gives the route.

A path to $v$ was found earlier with $g(v) = 10$. Now $u$ has been reached with $g(u) = 4$, and the edge u→v costs 3.

  1. Compare: $4 + 3 = 7 < 10$ — the route through $u$ is cheaper.
  2. Update the cost: $g(v): 10 \to 7$.
  3. Record the parent: $\mathrm{parent}(v) \leftarrow u$. (Had the sum been 12, nothing would change.)

Relaxation only ever lowers $g$. A finite $g(v)$ is always the cost of a real path that exists, so it is an upper bound on the true shortest cost. The question every algorithm must answer is: when can we be sure that $g(v)$ will not go any lower?

Dijkstra's algorithm

Imagine pouring water in at S and letting it flow through pipes whose lengths are the edge costs. The water reaches the nodes in order of their distance from S. Dijkstra simulates this: it always takes the nearest node that is not finished yet, declares its cost final, and relaxes its outgoing edges. Because no cost is negative, any other way into that node would have to pass through something even farther away — so nothing can beat it later.

Two sets keep the bookkeeping:

  • OPEN — nodes discovered but not final yet: a priority queue ordered by $g$. EXTRACT_MIN pops the smallest key; INSERT_OR_UPDATE inserts a node or lowers its key; PATH traces the parents back.
  • CLOSED — nodes already expanded; their $g$ is final.
$$u \in \argmin_{v \in \mathrm{OPEN}} g(v)$$

With all edge costs ≥ 0, the node with the smallest $g$ in OPEN has its final shortest cost: every other unfinished node already has a $g$ at least as large, and continuing through it only adds non-negative costs.

With a binary heap Dijkstra takes about $O((|V| + |E|)\log|V|)$ time. On a grid it expands nodes in growing rings of equal cost around S — it has no idea where the goal is, which is exactly what A* fixes.

A*: adding a sense of direction

Dijkstra asks only "how far have I come?". A* also asks "how far do I probably still have to go?" and picks the node whose estimated total trip is smallest. A route that has been cheap so far but heads away from the goal stops looking attractive. The estimate is called the heuristic $h$ — for a robot on a map, typically the straight-line or Manhattan distance to the goal.

$$f(v) = g(v) + h(v), \qquad u \in \argmin_{v \in \mathrm{OPEN}} f(v)$$
  • $g$: actual cost of the path found to $v$; $h$: estimate of the remaining cost from $v$ to G; $f$: the priority used to pick candidates.
  • Only the order of processing changes. What is minimized is still the real path cost: relaxation (lines 10–13) uses real edge costs exactly as in Dijkstra; only lines 03 and 14 insert with the key $g + h$.
  • $h = 0$ makes A* identical to Dijkstra. With a consistent $h$ and $h(G) = 0$, both find an optimal path.

Heuristic from the slides: $h(A) = 5$, $h(B) = 4$, $h(C) = 2$, $h(D) = 9$, $h(G) = 0$. The slides do not show $h(S)$ or $h(E)$; we use $h(S) = 7$ and $h(E) = 4$, which keep $h$ consistent.

Good heuristics: admissible and consistent

A heuristic is a guess about the remaining cost. Two properties make the guess safe. Admissible: the guess is never more than the truth — it is optimistic, like a straight-line distance that can never exceed the real road distance. Consistent: the guess never drops by more than you actually pay when you take one step — moving along one edge can lower the estimate by at most that edge's cost. Optimism guarantees you don't skip the best route; consistency also guarantees you never have to revisit a node.

DefinitionGuarantee
Admissible
all nodes		$0 \le h(v) \le h^{*}(v)$, where $h^{*}(v)$ is the true shortest cost from $v$ to G — never overestimates the remaining costoptimal path, if CLOSED nodes whose $g$ improves are put back into OPEN (re-expansion allowed)
Consistent
all edges		$h(u) \le c(u,v) + h(v)$ for every edge, and $h(G) = 0$ — a triangle inequalityoptimal path without re-expansion: a node popped with the minimum $f$ already has its shortest $g$

Consistency ⇒ admissibility when $h(G) = 0$: add the inequality along the shortest path from $v$ to G, and the $h$ terms telescope to $h(v) \le h^{*}(v)$. The converse does not hold in general — an admissible $h$ can still be inconsistent.

True costs to G: $h^{*}(S) = 8$, $h^{*}(A) = 6$, $h^{*}(B) = 5$ (slide 6: $2 + 3$), $h^{*}(C) = 3$, $h^{*}(D) = 16$, $h^{*}(E) = 6$.

  • Admissible? $5 \le 6$, $4 \le 5$, $2 \le 3$, $9 \le 16$, $7 \le 8$, $4 \le 6$ — yes, for every node.
  • Consistent? Check $h(u) \le c(u,v) + h(v)$ on each edge: A→B $5 \le 1 + 4$ (tight) · B→C $4 \le 2 + 2$ (tight) · A→C $5 \le 5 + 2$ · C→G $2 \le 3 + 0$ · B→E $4 \le 1 + 4$ · E→G $4 \le 6$ · D→E $9 \le 10 + 4$ · S→A $7 \le 2 + 5$ · S→B $7 \le 6 + 4$ · S→D $7 \le 1 + 9$ — yes.

$h(A) = 4$ is admissible ($h^{*}(A) = 1 + 3 = 4$) but inconsistent: $4 > c(A,B) + h(B) = 1$.

  1. Pop S: A gets $f = 1 + 4 = 5$, B gets $f = 4 + 0 = 4$.
  2. Pop B (f = 4): G gets $g = 7$. B is now CLOSED with $g = 4$.
  3. Pop A (f = 5): A→B gives $1 + 1 = 2 < 4$ — but B is already CLOSED.
  4. Without re-expansion G keeps $g = 7$ (wrong). With re-expansion B goes back to OPEN and G gets the true cost 5.

With a consistent $h$, f never decreases along a path, so A* behaves like Dijkstra on the "reduced" costs $c(u,v) - h(u) + h(v) \ge 0$. Among admissible heuristics, a larger $h$ (closer to $h^{*}$) means fewer expansions: $h = 0$ is the weakest (plain Dijkstra), $h = h^{*}$ walks straight to the goal.

Weighted A*: faster, with a quality bound

Weighted A* turns up the volume on the heuristic: it trusts "how close to the goal does this look?" more than "how much has this cost so far?". The search dives toward the goal greedily and usually finds a route much sooner — but it may lock onto a route that is not the cheapest. The weight ε sets the deal: the route you get never costs more than ε times the optimum.

$$f_\varepsilon(v) = g(v) + \varepsilon\,h(v), \quad \varepsilon \ge 1, \qquad J(P) \le \varepsilon\,J^{*}$$
  • ε = 1 is ordinary A*. ε > 1 aims to find a first path quickly; it favors nodes with small $h$ and may miss the optimum.
  • ε changes only the priority. Updates still use the real edge costs: if $g(u) + c(u,v) < g(v)$, update $g(v)$ and parent($v$).
  • A larger ε does not always mean fewer expansions — a greedy dive can run into a dead end and have to back up.
  1. Pop S ($f = 0 + 2 \cdot 7 = 14$): A $2 + 10 = 12$, B $6 + 8 = 14$, D $1 + 18 = 19$.
  2. Pop A (12): B improves to $g = 3$, $f = 3 + 8 = 11$; C gets $g = 7$, $f = 7 + 4 = 11$.
  3. Tie at 11; breaking toward the larger $g$ pops C: G gets $g = 10$, $f = 10$.
  4. Pop G (10) → stop. Route S→A→C→G, cost 10, after only 3 expansions.

Check the bound: $10 \le 2 \times 8 = 16$ — near-optimal, not optimal. Had the tie gone to B, this run would have found the 8-cost route: with ε > 1, small details decide which route you get.

Reusing results: ARA*, the anytime planner

A robot often has a deadline — say 100 ms to produce a plan. ARA* hands over a usable route almost immediately (large ε), then keeps working in whatever time remains, lowering ε step by step and polishing the route. What makes this cheap: everything learned so far stays valid. The stored $g$ values are costs of real paths and the parents still describe real routes; only the priorities need recomputing with the new ε.

Keep the graph and $h$ fixed and lower only ε. Continue from the stored $g$ and parent, and recompute $f_\mathrm{new}(v) = g(v) + \varepsilon_\mathrm{new}h(v)$ for the candidates — old path costs are not compared with $h$ directly. During the search the usual update applies: if $g(u) + c(u,v) < g(v)$, then $g(v) \leftarrow g(u) + c(u,v)$ and parent($v$) ← $u$; here $g(u)$ is the starting value for the new candidate and $g(v)$ the value to beat.

① Prepare candidatesOPEN ← OPEN ∪ INCONS; key ← g + εh; CLOSED ← ∅, INCONS ← ∅

② Search to the stop ruleuntil the smallest key in OPEN ≥ g(G), with g(G) < ∞

INCONS holds nodes whose $g$ dropped after they were already expanded in the current round. They are not re-expanded within the round (that keeps each round fast and its bound valid) but rejoin OPEN at the start of the next round. $g$ and parent persist between rounds, and finishing the ε = 1 stage gives the global optimum. (Conditions: finite graph, positive edge costs, consistent $h$, $h(G) = 0$, and a path exists.)

Round 1 (ε = 2) — the Weighted A* run above: it expands S, A and C and stops with $g(G) = 10$, because the smallest key in OPEN (G at 10) is ≥ $g(G)$. Stored: $g(S) = 0$, $g(A) = 2$, $g(B) = 3$, $g(C) = 7$, $g(D) = 1$, $g(G) = 10$; OPEN = {B, D, G}; INCONS is empty. Deliver S–A–C–G (10), guaranteed ≤ 16.

Round 2 (ε = 1) — recompute keys: B $3 + 4 = 7$, G $10 + 0 = 10$, D $1 + 9 = 10$; clear CLOSED.

  1. Pop B (7): C improves $7 \to 3 + 2 = 5$ (key 7); E gets $g = 4$ (key 8).
  2. Pop C (7): G improves $10 \to 5 + 3 = 8$ (key 8).
  3. The smallest key is now 8 ≥ $g(G) = 8$ → stop. Deliver S–A–B–C–G (8) — optimal.

Round 2 needed only 2 expansions where a fresh A* needs 4. That saving is the whole point of reuse.

When the map changes

Maps are not fixed: a door closes, a road is blocked, a sensor finds that an area is free after all. Now the real edge costs change, not ε. A change can break the current route (it can no longer be driven) or make it second-best (something cheaper appeared). Either way the plan must be re-examined — ideally without throwing away everything already known.

Restarting A* from scratch after every change wastes work, because most stored $g$ values are still correct. The next step is to find exactly which nodes need reprocessing, starting from the previous $g$ — that is what LPA* does.

LPA*: repair instead of restart

Think of a spreadsheet: when you change one cell, only the cells that depend on it are recalculated. LPA* keeps the old cost $g$ of every node and also computes what the cost should be from the predecessors' current values — this one-step look-ahead is called rhs. Wherever the two disagree, something changed nearby, and only those nodes go into OPEN. Nodes where $g$ and rhs agree are never touched.

$$\mathrm{rhs}(S) = 0, \qquad \mathrm{rhs}(v) = \min_{u \in \mathrm{Pred}(v)}\left[g(u) + c(u,v)\right] \quad (v \ne S)$$
  • $g(v)$: cost stored by the previous search. rhs($v$): the candidate recomputed from the predecessors' current $g$.
  • $g(v) = \mathrm{rhs}(v)$: locally consistent — nothing to do. (A different notion from heuristic consistency.)
  • $g(v) \ne \mathrm{rhs}(v)$: put $v$ in OPEN. Checking starts at the head node of the changed edge.
CaseMeaningAction when popped
$g > \mathrm{rhs}$ (overconsistent)a cheaper way in has appearedadopt it: $g \leftarrow \mathrm{rhs}$, then update the successors
$g < \mathrm{rhs}$ (underconsistent)the stored cost relied on something that got worseinvalidate: $g \leftarrow \infty$, then update the successors and the node itself

OPEN is ordered by a two-part key that uses $m(u) = \min(g(u), \mathrm{rhs}(u))$ in place of A*'s $g$:

$$K(u) = [k_1, k_2] = [m(u) + h(u),\; m(u)]$$

$k_1$ (the estimated total cost) decides first; $k_2$ breaks ties. UpdateVertex($v$) recomputes rhs($v$), then puts $v$ in OPEN (or refreshes its key) if $g \ne \mathrm{rhs}$, or removes it if $g = \mathrm{rhs}$. The search stops when the goal has $g = \mathrm{rhs}$ and the smallest key in OPEN is ≥ the goal's key.

D* Lite: replanning while the robot moves

LPA* stores costs from the start. But a robot moves: after every step its "start" is somewhere else, and all those costs would change. D* Lite flips the search around and stores, for every node, the cost from that node to the goal — the cost-to-go. The goal doesn't move, so these values stay valid wherever the robot is. To drive, the robot simply steps to the neighbor with the smallest "edge cost + cost-to-go", like water running downhill. When it discovers a change, D* Lite repairs the cost-to-go values exactly the way LPA* repairs $g$.

A* · LPA*D* Lite
$g$ meanscost from the start to the node (S→v)cost from the node to the fixed goal (v→G)
$h$ meansestimate from the node to the goal (v→G)estimate from the current position S to the node (S→v)
$$\mathrm{rhs}_\mathrm{to}(G) = 0, \qquad \mathrm{rhs}_\mathrm{to}(u) = \min_{v \in \mathrm{Succ}(u)}\left[c(u,v) + g_\mathrm{to}(v)\right] \;\; (u \ne G), \qquad v_\mathrm{next} \in \argmin_{v \in \mathrm{Succ}(B)}\left[c(B,v) + g_\mathrm{to}(v)\right]$$

Work backward from G: $g_\mathrm{to}(G) = 0$, $g_\mathrm{to}(C) = 3$, $g_\mathrm{to}(E) = 6$, $g_\mathrm{to}(B) = \min(2 + 3, 1 + 6) = 5$, $g_\mathrm{to}(A) = \min(5 + 3, 1 + 5) = 6$, $g_\mathrm{to}(D) = 10 + 6 = 16$, $g_\mathrm{to}(S) = \min(2 + 6, 6 + 5, 1 + 16) = 8$.

A cost from the start depends on where "the start" is: from S, B is 3 away ($g_\mathrm{from\,S}(B) = 3$); once the robot reaches A, only 1 ($g_\mathrm{from\,A}(B) = 1$). The cost-to-go of B, 5, does not care where the robot is.

The robot has driven S→A→B and plans to continue B→C→G. At B its sensors show that B→C is closed. Keep the repair (computation) separate from the move (action):

  1. $\mathrm{rhs}_\mathrm{to}(B) = \min\left(c(B,C) + g_\mathrm{to}(C),\; c(B,E) + g_\mathrm{to}(E)\right) = \min(\infty + 3,\; 1 + 6) = 7 \ne 5$. B has $g < \mathrm{rhs}$: invalidate, $g_\mathrm{to}(B)$: 5 → ∞.
  2. A's cost-to-go relied on B: $\mathrm{rhs}_\mathrm{to}(A) = \min(5 + 3, 1 + \infty) = 8 \ne 6$. A has the smaller key (6 < 7), so it goes first: $g_\mathrm{to}(A)$: 6 → ∞.
  3. B is popped with key 7: $g_\mathrm{to}(B)$: ∞ → 7. The robot's own node is consistent again and nothing in OPEN has a smaller key → stop repairing.
  4. Move: compare B's successors: via C, $\infty + 3$; via E, $1 + 6 = 7$ → drive B→E. Remaining cost 7.

The key modifier km

OPEN is sorted by keys that include $h$ measured from the robot's position. Every time the robot moves, all of those keys are slightly out of date. Recomputing them all would be expensive, so D* Lite keeps one running correction, $k_m$ — "how far the robot has moved, in heuristic terms" — and adds it to every new key. Old keys then remain lower bounds of the correct ones: when an old node reaches the front of the queue, its key is recomputed, and if it was stale the node is simply put back.

$$K(s) = \left[m(s) + h(S, s) + k_m,\; m(s)\right], \qquad k_m \leftarrow k_m + h(S_\mathrm{old}, S_\mathrm{new}), \qquad m(s) = \min\left(g(s), \mathrm{rhs}(s)\right)$$

Manhattan grid, unit steps; X keeps $g = 8$ and rhs = 7, so $m(X) = 7$.

  1. Robot at A: $K_\mathrm{old}(X) = [7 + 5 + 0, 7] = [12, 7]$.
  2. Robot moves A→B: $k_m$: 0 → 3.
  3. $K_\mathrm{new}(X) = [7 + 4 + 3, 7] = [14, 7]$. The stored key (12, 7) is smaller, so when X is popped it is reinserted with (14, 7).

Without the correction, $k_1 = 7 + 4 = 11$ would be compared with keys computed from A — apples and oranges.

Why it works: $h$ is non-negative, admissible and satisfies the triangle inequality $h(S_\mathrm{new}, s) + h(S_\mathrm{old}, S_\mathrm{new}) \ge h(S_\mathrm{old}, s)$ — here $4 + 3 \ge 5$. $k_m$ is added only to keys; it never changes $g$, rhs or the real move costs.

Huge maps I: HPA* (hierarchical path-finding)

Plan like a traveler: first decide which cities and highway exits to pass through, then work out the streets inside each city. HPA* cuts the grid into clusters, picks a few portals on the borders between clusters, and remembers in advance how much it costs to cross each cluster from one portal to another. A query then runs A* on this small "portal graph" and only afterwards fills in the cell-by-cell path.

  1. Preprocess (once per map): split into clusters → choose portals → store the shortest cost inside each cluster between its portals, $c(p, q) = \min J(P)$ over p→q paths P that stay in the same cluster. A high-level edge stands for an inner path and its cost; neighboring clusters are joined by crossing edges.
  2. Query: insert S and G into the abstract graph (connect them to the portals of their clusters) and run A* there.
  3. Refine: replace each chosen abstract edge by its stored grid path.

The inner path a→c (cost 6) is computed once and stored. With S and G inserted, the candidates are S–c–d–g–h–G = 4 + 1 + 5 + 1 + 7 = 18 and S–a–b–e–f–G = 6 + 1 + 8 + 1 + 4 = 20, so A* returns 18. Refined into grid cells, the route is 2 cells longer than the true shortest path (16): optimality holds on the abstract graph only, because the choice of portals can rule out the true shortest path.

The trade-off: the abstract graph is tiny, so queries are fast, and the preprocessing is shared by every query — at the price of a slightly longer route. More portals means better routes but a bigger abstract graph.

Huge maps II: Contraction Hierarchies

Car navigation on a country-sized road network must answer millions of queries on a map that rarely changes. Contraction Hierarchies spend time once, in advance: they rank the nodes by importance and add "express lanes" (shortcuts) that skip over unimportant nodes. A query then searches only upward in importance — from the start and from the goal at the same time — and meets in the middle on the express network. The answer is still exactly optimal.

  • Contracting a node $v$ removes it from the working graph. For each pair of neighbors $u, w$ whose shortest connection ran through $v$, a shortcut u→w with the same cost is added — unless a witness path that avoids $v$ is just as cheap. The rule: add the shortcut if the shortest detour avoiding $v$ costs more than the path through $v$.
  • Nodes are contracted in some order (e.g. smallest Edge Difference first, where Edge Difference = shortcuts added − edges removed); a node's position in that order is its rank.
  • A query runs Dijkstra from S and from G, each relaxing only edges toward higher rank; where they meet gives the route, and shortcuts are unpacked into the original roads (u→w is returned as u→v→w). Original nodes and shortcuts are stored apart from the working graph; of duplicate edges with the same direction and endpoints, only the cheaper is kept.

Shortcut decision: through v, u→w costs 2 + 3 = 5; the best witness avoiding v is u→z→w = 3 + 3 = 6 > 5, so add the shortcut u→w (5). Edge Difference = 1 added − 2 removed = −1.

Query speed: on slide 19's 37-node road grid, Dijkstra expands 30 nodes; the CH query expands 8 in total over both directions (preprocessing excluded; the meeting node counted twice) — and both return the same path cost, 30.

If z–w cost 2 instead, the witness u→z→w would cost 5 ≤ 5 and no shortcut would be needed.

Executing the route with an FSM

Finding a route is not the same as driving it. Something must decide, at every moment, whether to keep following the route, pause (a person stepped in front, an operator pressed "wait"), compute a new route (the current one became invalid), or stop because the mission is done. A finite-state machine (FSM) is the simplest reliable way to write these rules down: a small set of modes, and clear conditions for switching between them.

Inputs $z = (a, d, r)$: $a$ = hold request, $d$ = mission done, $r$ = route valid for the current position and map.

States $q$: FollowRoute (runs a valid route), Hold (paused), Replan (one replan on entry, then the new route is verified), Arrived (mission over).

$$q_{k+1} = \delta(q_k, z_k)$$

Guards and their priority

Several inputs can be true at once — a hold request may arrive just as the route becomes invalid. The design must say which wins. The slides' policy checks a → d → r in that order, a design choice that puts a hold request first:

$$\text{Hold}: a \qquad \text{Arrived}: \neg a \wedge d \qquad \text{Replan}: \neg a \wedge \neg d \wedge \neg r \qquad \text{FollowRoute}: \neg a \wedge \neg d \wedge r$$

The four guards are mutually exclusive and together cover every input, so exactly one state is chosen at every step — no ambiguity and no gaps.

Hysteresis: stop flip-flopping between routes

Suppose two routes are both fine and cost almost the same. Their costs wobble a little with traffic or sensor noise, so "always take the cheaper one" makes the robot switch back and forth — unsettling for passengers and bad for control. Hysteresis adds a margin: switch only when the other route is better by more than δ. Small wobbles are ignored; big, real differences still win.

$$\Delta J = J_A - J_B, \qquad A \to B \text{ if } \Delta J > \delta, \qquad B \to A \text{ if } \Delta J < -\delta, \qquad -\delta \le \Delta J \le \delta: \text{ keep the current choice}$$

ΔJ ≈ (0.5, −0.3, 0.6, −0.1, 2.6, 1.1, −0.4, −2.6), initial choice $R_A$.

  • Always cheapest (B whenever ΔJ > 0): B, A, B, A, B, B, A, A → 6 switches.
  • Hysteresis, δ = 2: stay on A until ΔJ = 2.6 > 2 at k = 4 → B; stay on B until ΔJ = −2.6 < −2 at k = 7 → A → 2 switches.

Compare the costs with the same current position, goal and map — otherwise ΔJ means nothing. And hysteresis applies only between valid routes: if the current route becomes invalid, replace it immediately, regardless of the cost difference. A larger δ means fewer switches, but possibly staying up to δ longer on a worse route.

Using step 5 of the slide-graph Dijkstra trace, explain why the search must not stop when the goal is first discovered.

At step 5, G is discovered through E with $g = 10$, but C (g = 5) is still in OPEN and C→G costs only 3, so a route of cost 8 exists. A discovered node's $g$ is only an upper bound. When G is popped as the minimum, every other OPEN node has $g \ge g(G)$ and costs are non-negative, so nothing can improve it any more — only then is $g(G)$ final.

In ARA*, why can the stored $g$ values and parents be reused when ε is lowered, while the keys in OPEN must be recomputed?

A stored $g(v)$ is the cost of a real path to $v$ that was actually found; that fact does not depend on ε, so it remains a valid upper bound, and the parents still describe that path. The keys $g + \varepsilon h$ do depend on ε — they are only priorities — so with a new ε they must be recomputed (step ① of the loop). Reusing $g$ is what lets round 2 of the slide example finish in 2 expansions instead of 4.

HPA* returned a route of cost 18 where the optimum is 16. Suggest two ways to get closer to 16 and say what each costs.

  • More portals per cluster border (or smaller clusters): the abstract graph contains more of the possible crossings, so better routes become available — at the price of more preprocessing and a larger abstract graph to search.
  • Post-smoothing / local re-search: after refinement, run A* in the grid inside a corridor around the refined path to straighten detours — extra time per query, but usually close to optimal.

In LPA*, what do $g > \mathrm{rhs}$ and $g < \mathrm{rhs}$ mean physically? Why must the $g < \mathrm{rhs}$ case also update the node itself?

$g > \mathrm{rhs}$: a cheaper way into the node has appeared (e.g. an edge got cheaper), so the stored cost is too high — simply adopt rhs, as in a normal relaxation. $g < \mathrm{rhs}$: the stored cost relied on something that got worse or disappeared (e.g. a closed edge), so it is too optimistic and cannot be trusted. Setting $g = \infty$ throws the bad value away; afterwards the node usually has a finite rhs from its other predecessors, which makes it overconsistent — so it must go back into OPEN to receive its new, correct cost (like C going (5, 7) → (∞, 7) → (7, 7) on slide 13).

Why does D* Lite store cost-to-go (node → goal) rather than cost-from-start, and how does the robot use those values to move?

The robot's position — the "start" — changes with every step, so costs measured from the start would all change constantly. The goal is fixed, so costs to the goal stay valid as the robot moves; only edge changes require repairs. To move, the robot takes the successor with the smallest $c(\text{here}, v) + g_\mathrm{to}(v)$ — on slide 15, after the repair at B, that is E with 1 + 6 = 7.
