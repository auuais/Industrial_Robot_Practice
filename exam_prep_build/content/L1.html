Sense, compute, act

Lecture 1 defines a robot by three basic functions that repeat in a loop:

StageWhat happensTypical hardware
1 · SenseAcquire information about the environment and about the robot's own internal state with sensors.Camera · LiDAR · IMU · wheel encoder
2 · ComputeProcess the data and calculate the values needed for the next action.Embedded computer running algorithms
3 · ActSend the result to actuators, which change the robot's motion state.Motors · steering · drive system

The loop closes because acting changes what the robot senses next. Sensors split into two families you will meet again and again: exteroceptive sensors look outward (camera, LiDAR, radar, GNSS), while proprioceptive sensors measure the robot itself (wheel encoders, IMU, joint encoders, steering-angle sensors).

The course uses the autonomous vehicle as its main example, but the slides stress that manipulators, quadrupeds and humanoids follow the same engineering approach: model the system, work out its state, then generate a suitable action. Lecture 2 accordingly treats both a robot arm and a car.

The intelligent robot software stack

Autonomous motion needs four layers. Each one consumes the output of the previous one:

PerceptionUses sensor data to find the structure of the surroundings and the position and motion of objects: lanes, objects, free (drivable) space. State estimationUses measurements and a system model to estimate the robot's current state: position $(X, Y)$, heading $\psi$, velocity $v$. PlanningFrom the current state, the environment and a goal, produces a path or a drivable trajectory. ControlComputes steering and acceleration inputs that shrink the error between the reference path and the current state.

Each layer is only as good as the one before it. A controller cannot track a path well if the state estimate is biased, and the estimate cannot be better than the calibration of the sensors that feed it. That is why the course starts with models and calibration.

The five building blocks, one by one

Modeling

Express the behavior of the real system as a relation between inputs, states and parameters:

$$\mathbf{x}_{k+1} = f(\mathbf{x}_k, \mathbf{u}_k; \boldsymbol\theta)$$

For a car (Lecture 2): the state is position $(X, Y)$, heading $\psi$ and speed $v$; the input is the steering angle $\delta$ and acceleration $a$; the parameters are fixed properties such as mass $m$ and wheelbase $L$. The model predicts the next state from the current state and input. A good test of understanding: a state changes because of the dynamics, an input is chosen by us, a parameter is a constant we may have to estimate.

Perception

Sensor data → calibration → perception. Before detections can be trusted, each sensor needs its intrinsic parameters (e.g. camera focal length and distortion), the extrinsic pose between sensors, time synchronization and alignment into a common coordinate frame. Only then can the outputs — objects, lanes, drivable area, relative distance and speed — be fused. Chapter 3 is entirely about this calibration step.

Estimation

Lecture 1 separates two kinds of estimation:

State estimation (W05–06)Parameter estimation (W07)
QuestionWhat is the current state?What are the model parameters?
RecipePredict with the model, $\hat{x}_{k|k-1} = f(\hat{x}_{k-1|k-1}, u_{k-1}; \hat\theta)$, then update with the measurement $z_k$ to get $\hat{x}_{k|k}$Collect inputs and measurements $\{u_k, z_k\}_{k=1}^{N}$ and solve $\hat\theta = \argmin_\theta J(\theta)$
Keywordsdead reckoning, KF / EKF, sensor fusion, localization, SLAMleast squares, system identification, SINDy, calibration
Output$\hat{x}_{k|k}$: position $(\hat X, \hat Y)$, heading $\hat\psi$, velocity $\hat v$$\hat\theta = [\hat m, \hat L, \hat C, \dots]$: mass, wheelbase, tire/actuator parameters

The two are linked: estimated parameters update the robot model, and the model is what the state estimator uses for prediction.

Notation: $\hat{x}_{k|k-1}$ reads "estimate of $x$ at step $k$ using data up to step $k-1$" — the prediction. Lecture 4 writes the same thing as $\hat{x}_k^-$, and $\hat{x}_{k|k}$ as $\hat{x}_k^+$.

Planning

Planning decides a path and behavior from the goal and the surroundings and produces a drivable trajectory, in three stages: global planning (a route on a graph with edge costs: Dijkstra, A*), behavior planning (a finite-state machine choosing lane keep, lane change, stop/yield) and local or trajectory planning (Bézier curves, Frenet frame, candidate trajectories ranked by cost). The output is a reference trajectory $\mathcal{T}_{\mathrm{ref}} = \{(x_i, y_i, \psi_i, v_i)\}_{i=0}^{N}$.

Control

Closed-loop tracking: compare the reference with the estimated state to get the tracking errors — lateral error $e_y$ and heading error $e_\psi$ — and let the controller compute $\mathbf{u}_k = [\delta_k, a_k]^\T$. The vehicle moves, state estimation measures the new state, and the loop repeats (feedback). The later weeks cover Pure Pursuit, Stanley and the dynamic bicycle model (W12), then Lyapunov stability, sliding-mode control, LQR and MPC with costs and constraints (W13).

  • Time. A measurement is useless without its timestamp: joint angles at the wrong time (ch. 2), camera–IMU time offset (ch. 3), observation gaps in a Kalman filter (ch. 4).

Practice questions

A delivery robot has: a 2-D LiDAR, wheel encoders, an IMU, an onboard GPU computer running path planning, two drive motors and a steering servo. Sort these into sense, compute and act, and say which sensors are proprioceptive.

Sense: LiDAR, wheel encoders, IMU. Compute: the GPU computer and the planning software. Act: drive motors and steering servo. Proprioceptive (measure the robot itself): wheel encoders and IMU. The LiDAR is exteroceptive (measures the environment).

For the car model $\mathbf{x}_{k+1} = f(\mathbf{x}_k, \mathbf{u}_k; \boldsymbol\theta)$, classify each quantity as state, input or parameter: yaw angle, steering-angle command, wheelbase, speed, acceleration command, vehicle mass, $X$-position, tire cornering stiffness.

State: yaw angle $\psi$, speed $v$, position $X$ (they evolve through the dynamics). Input: steering command $\delta$ and acceleration command $a$ (chosen by the controller). Parameter: wheelbase $L$, mass $m$, cornering stiffness $C$ (constant properties of the vehicle — the ones parameter estimation tries to identify).

Explain the difference between state estimation and parameter estimation, giving one example of each from this course.

State estimation answers "where is the robot now?" — a quantity that changes every step and is estimated recursively by predicting with the model and correcting with each new measurement (e.g. the Kalman filter estimating position and velocity in Lecture 4, or the EKF estimating pose in Lecture 6). Parameter estimation answers "what constants describe the system?" — quantities that do not change, estimated from a whole batch of recorded data by minimizing a cost $J(\theta)$ (e.g. camera intrinsics $K$ and distortion in Lecture 3, or a wheelbase identified from driving data). They feed each other: better parameters give a better model for prediction.

Why does calibration come before perception and state estimation in the stack? Describe what goes wrong in each later layer if the camera–LiDAR extrinsic is off by a few degrees.

Every later layer assumes that sensor data are already expressed correctly in a common frame and on a common time axis; calibration is what makes that true. With a rotated camera–LiDAR extrinsic, LiDAR points projected into the image land beside the objects they belong to, so perception associates wrong depths with detections; the error grows with distance (a few degrees is tens of centimetres at 10 m). State estimation then fuses inconsistent measurements, producing a biased or jumpy pose; planning places obstacles in the wrong place, and control tracks a path that is wrong to begin with. None of the later layers can detect the problem on its own, because the error looks like a valid measurement.

A path-tracking controller performs poorly even though the planned path is smooth and the controller gains were tuned in simulation. Using the four-layer stack, name two upstream causes worth checking and one model-related cause.

  • State estimation: a biased or delayed pose estimate (e.g. odometry drift, a wrong sensor time offset) makes the controller correct errors that do not exist.
  • Perception / calibration: a wrong extrinsic shifts the lane or path relative to the vehicle, so the reference itself is displaced.
  • Model: the controller was designed on a model whose parameters $\theta$ (wheelbase, steering response, tire behavior) do not match the real vehicle — e.g. a kinematic model used at high lateral acceleration, or a steering actuator lag ignored (both covered in Lecture 2).
