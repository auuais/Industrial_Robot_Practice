Lecture 1 · Introduction

Course map: what an intelligent robot does

Sense–compute–act, the four software layers, and how modeling, estimation and optimization connect.

Questions

Why is a robot described as a loop of sense, compute and act rather than a one-way pipeline?

Every action changes the robot's state and its surroundings, which changes what it senses next; the next decision depends on that new information. Closing the loop is what lets a robot correct its own mistakes and react to disturbances. A one-way pipeline (plan once, execute blindly) cannot notice that a wheel slipped or an obstacle moved.

What is the difference between exteroceptive and proprioceptive sensors, and why does a robot usually need both?

Proprioceptive sensors (wheel encoders, IMU, joint encoders) measure the robot itself: smooth, high-rate, always available, but their errors accumulate because they only measure change. Exteroceptive sensors (camera, LiDAR, GNSS) measure the world: they give absolute references but are slower, noisier, and can drop out. Together they cover each other's weakness — proprioception for smooth short-term motion, exteroception to stop long-term drift.

How do you decide whether a quantity is a state, an input or a parameter? Use a car's mass, speed and steering command as examples.

Ask who changes it and how fast. A state evolves through the system's own dynamics and must be tracked over time (speed). An input is chosen from outside, usually by the controller (steering command). A parameter is a property of the system that is constant, or changes so slowly it is treated as constant (mass). The same physical quantity can move category depending on the model — a car's mass becomes a state if you model fuel burn or a changing payload.

Explain why the layers of the stack (perception → estimation → planning → control) depend on each other in order. What is the consequence for debugging?

Each layer consumes the output of the one before: a planner plans from the estimated state, a controller tracks the planned path from the estimated state. An error upstream propagates downstream and often looks like a downstream fault — a jittery steering wheel may really be a jumpy pose estimate. So debugging should start upstream: verify calibration and estimation before retuning the controller.

State estimation and parameter estimation both "estimate from data". What fundamentally distinguishes them?

State estimation tracks something that changes every moment, so it runs recursively — predict with the model, correct with each new measurement — and keeps an up-to-date belief. Parameter estimation identifies constants, so it can use a whole batch of recorded data at once and solve one optimization problem. They feed each other: parameters make the model that the state estimator predicts with, and good state estimates are the data for identifying parameters.

Why is calibration treated as a prerequisite of perception rather than part of it?

Perception algorithms assume their inputs are already geometrically correct: pixels mapped through the right lens model, sensors expressed in a common frame, and data aligned in time. Calibration is what makes those assumptions true. If it is wrong, every downstream result is consistently wrong, and nothing in the perception algorithm can detect it, because the bad data still looks like valid data.

What does a controller need from state estimation, and what goes wrong if the estimate is delayed?

The controller compares the reference path with the robot's current state (position, heading, speed) to compute tracking errors. A delayed estimate describes where the robot was, so the controller reacts late to errors it should already have corrected; at speed this causes overshoot and oscillation, much like driving while looking at a video with a lag.

Planning is split into global, behavior and local/trajectory planning. Why not plan everything in one step?

The levels work on different scales of space and time. A global route over a road network changes rarely and can be planned slowly; behavior decisions (keep lane, change lane, yield) react to traffic every few seconds; a local trajectory must respect vehicle dynamics and nearby obstacles and is recomputed many times per second. Splitting keeps each problem small enough to solve at the rate it needs.

The lecture says manipulators, quadrupeds and cars follow the same engineering approach. What is that common approach, and what changes between platforms?

The approach is: model the system, estimate its state, then generate an action — with sensing and feedback closing the loop. What changes is the content of each step: the kinematic model (joint chain vs. wheels vs. legs), the sensors used, the constraints (joint limits, no lateral slip, contact forces) and the control objective. The same estimation and optimization tools apply to all of them.

Why does optimization appear "underneath" so many parts of the course instead of being one isolated topic?

Many robotics tasks are naturally stated as "find the values that best explain the data, or best achieve the goal, subject to limits". Calibration finds parameters that best explain images, pose-graph SLAM finds the trajectory that best agrees with all measurements, the Kalman gain is chosen to minimize error variance, and MPC chooses inputs that best track a path within actuator limits. Once a problem is written as a cost plus constraints, the same solvers work for all of them.
